# Рантбук: эксплуатация WELCOME

Документ для того, кто ведёт этот продукт после нас. Собран из реальных событий
этой сессии, а не из предположений: каждая строка ниже что-то стоила.

## 1. Деплой

```bash
vercel deploy --prod --yes --scope nikiti4
```

- **`--scope nikiti4` обязателен.** Локальная сессия Vercel CLI может оказаться
  под другим аккаунтом (у нас так и было), и без явного scope деплой падает с
  `Error: Not authorized`. Проект живёт в команде `nikiti4`.
- **Миграции — всегда до кода.** Порядок обратный тому, что кажется удобным:
  сначала `DATABASE_URL=$NEON_CONN_DIRECT node scripts/migrate.mjs`, потом деплой
  кода. Обратный порядок уже один раз дал 87 ошибок на проде.
- Прод-переменные: `APP_BASE_URL=https://welcome.colmogravity.net`,
  `RESEND_FROM=WELCOME <no-reply@send.colmogravity.net>`.
- После деплоя — быстрая проверка: `curl -s https://welcome.colmogravity.net/api/health`.

## 2. Здоровье и что оно значит

`GET /api/health` отдаёт:

| Поле | Смысл |
|---|---|
| `status`, `db` | живость и доступность базы |
| `worker` | свежий ли последний плановый тик относительно `WORKER_FRESHNESS_SECONDS` |
| `worker_last_tick_age_seconds` | возраст тика **числом** — порог для мониторинга выбирает эксплуатация |
| `pending_jobs` | сколько заданий доставки ещё не завершено |
| `oldest_pending_job_age_seconds` | возраст самого старого незавершённого задания |

Важно: раньше проба записи в health **обновляла пульс воркера**, из-за чего
`worker: up` показывался даже на деплое с мёртвым воркером. Это исправлено —
теперь сигнал честный, и его нельзя «случайно» оживить проверкой.

Окружение воркера: тик дёргается кроном платформы, а доставка дополнительно
обрабатывается прямо в ответе запроса. Поэтому суточный крон на бесплатном
тарифе — норма, а не поломка.

## 3. Демонстрация продукта (то, что нужно показывать людям)

```bash
# вернуть демо-персон в состояние «сценарий можно показать снова»
node --import tsx scripts/demo-reset.mts --target="$DATABASE_URL" --i-know-this-is-production --dry-run
node --import tsx scripts/demo-reset.mts --target="$DATABASE_URL" --i-know-this-is-production

# сам сценарий двух людей на живом стенде (A приглашает, B открывает карточку по адресу из QR)
node scripts/two-user-walkthrough.mjs --target=https://welcome.colmogravity.net
```

- Предохранители сброса: список демо-адресов зашит в код, без явного
  `--i-know-this-is-production` инструмент отказывается работать с похожей на прод
  базой, перед удалением печатает план (сухой прогон), повторный запуск — no-op.
- Область удаления: **одно** знакомство в одном контексте события плюс его
  следствия. Журнал аудита не переписывается.
- Свежая пара для демо: демо-персона, которая **не** участник события, плюс
  `--unjoin`, возвращающий её в это состояние.

## 5. Секреты

- Прод-переменные — в Vercel (`--scope nikiti4`), секретные значения оттуда не читаются.
- Локальные прод-секреты — в `welcome/.env.deploy.secrets` (в git не попадает).
- Скачанные ключи Google — в `~/.openclaw-autoclaw/secrets/` с правами 600.
- `.gitignore` закрывает `.env*`, `client_secret_*.json` и `.secrets/`: Google отдаёт
  клиент именно под этим именем, и его чаще всего коммитят по ошибке.
- Проверка истории git на настоящие ключи выполнялась — их нет.

**Ротация ключа шифрования.** Механизм есть: каждый шифротекст хранит id ключа,
которым он запечатан (`<id>.<iv>.<ct>.<tag>`), и развёртывание может держать
несколько ключей одновременно — один АКТИВНЫЙ (им пишутся новые значения) и
сколько угодно ЧИТАЕМЫХ. Схему менять не нужно, миграции данных при выкатке нет.
Разбор «почему так» и риски — `docs-internal/security/KEY_ROTATION_ASSESSMENT.md`.

Переменные:

```
ENCRYPTION_KEY      активный ключ (обязателен, как и был; id = v1, если ниже не сказано иное)
ENCRYPTION_KEY_ID   id активного ключа — нужен только если он не v1
ENCRYPTION_KEYS     остальные ЧИТАЕМЫЕ ключи, "id:base64,id:base64"
```

Если задан только `ENCRYPTION_KEY` — это одно-ключевое развёртывание, и пишутся
ровно те же байты, что и раньше.

ВАЖНО: эти три переменные должны совпадать у ПРИЛОЖЕНИЯ и у КОМАНДЫ. Команда
читает только окружение, из которого её запустили: меняя ключ в Vercel, выставьте
те же значения и в своей оболочке (`export …` ниже), иначе команда будет работать
со своим keyring, а приложение — со своим, и census покажет не то, что видит
приложение.

Порядок (шаги 2 и 3 можно совмещать):

```bash
# 1. EXPAND — новый ключ добавлен ЧИТАЕМЫМ, активный пока старый
openssl rand -base64 32                                   # новый ключ
export ENCRYPTION_KEYS="v2:<новый ключ>"
pnpm key:rotate --dry-run                                  # активный v1, читаются v1 и v2

# 2. FLIP — активным становится новый ключ, старый остаётся читаемым
export ENCRYPTION_KEY="<новый ключ>"
export ENCRYPTION_KEY_ID=v2
export ENCRYPTION_KEYS="v1:<старый ключ>"

# 3. BACKFILL — пока dry-run не покажет ноль строк на старом id
pnpm key:rotate --dry-run                                  # CENSUS VERDICT + строки «and N more»
pnpm key:rotate                                            # перезапись; в конце — CENSUS AFTER

# 4. CONTRACT — только когда census читает ноль по старому id в каждой колонке
export ENCRYPTION_KEYS=""                                  # старый ключ больше не читается
```

Что смотреть в выводе команды (это и есть проверка, а не отчёт для вида):

- таблица по каждой колонке: `rows · current · stale · foreign · corrupt · null` —
  классы складываются в число строк таблицы;
- блоки по колонкам с ПЕРВИЧНЫМИ КЛЮЧАМИ всех строк, которые команда трогать
  откажется (`foreign` — ключа с таким id нет в keyring, `corrupt` — не payload или
  не расшифровывается под своим же id), и с id, который каждой строке нужен;
  `--limit=0` печатает их все; значения и ключи не печатаются никогда;
- `rows by key id` — по этой строке принимается решение о выводе ключа из
  `ENCRYPTION_KEYS`: должно быть ноль по выводимому id в КАЖДОЙ колонке;
- «NOTHING LEFT TO REWRITE, BUT NOT A ZERO» — перезаписывать нечего, но строки
  этот id ещё называют (прочитать их нельзя). Вывод ключа им не поможет и хуже не
  сделает; чтобы их прочитать, нужен ключ, которым они запечатаны, — вернуть его в
  `ENCRYPTION_KEYS`.

Откат: шаги 1–3 обратимы сменой переменных окружения назад в любой момент до
шага 4. После шага 3 старых строк не осталось, поэтому откат касается только
OAuth-state (ниже).

**Единственный видимый пользователю эффект** — на шаге 2. MAC у OAuth-`state`
выводится из `ENCRYPTION_KEY` (HKDF, `src/lib/oauth-state.ts`), а не из keyring,
поэтому при смене этого ключа перестают проверяться state, выданные за последние
10 минут: пользователь в середине перехода на Google получает отказ и начинает
заход заново. Потери данных нет, state одноразовый и короткоживущий; окно — десять
минут. Оставить так (вариант A) или носить id ключа внутри state (вариант B) —
решение того, кто делает flip; цена обоих расписана в assessment. Для шага 4 окно
уже неактуально: state живёт 10 минут.

**Чего эта команда НЕ чинит:** строки, которые уже нечитаемы (ключ потерян). Они
перечислены в census с primary key и остаются как есть — перезапись означала бы
выдумать значение или удалить строку, а это не «ротация ключа».

## 6. Грабли, на которые мы уже наступали

| Симптом | Причина | Что делать |
|---|---|---|
| Строки перестали читаться после смены ключа (`no encryption key with id …`) | сменили `ENCRYPTION_KEY`, не сохранив id: id — это ИМЯ ключа, и строки, помеченные старым id, теперь нечем открыть | менять пару `ENCRYPTION_KEY` + `ENCRYPTION_KEY_ID`, а старый ключ оставлять в `ENCRYPTION_KEYS`; `pnpm key:rotate --dry-run` показывает такие строки как `foreign`/`corrupt` с primary key |
| `Error: Not authorized` при деплое | CLI-сессия под другим аккаунтом | `--scope nikiti4` |
| e2e падает за 3 секунды | работает `pnpm dev`, держится блокировка | остановить дев-сервер |
| Страница по слагу отдаёт 500 | в SQL уходило `id = $1 OR slug = $1`, Postgres пытался привести слаг к uuid | ветвление по `isUuid`; проверять страницы тем же способом, что их API-маршруты |
| Тест «зелёный», но ничего не проверяет | утверждение не отличает видимый текст от скрытого для скринридера | проверять по вычисленным стилям или доступному имени |
| Флак в тесте подписи | зафиксированный символ совпадал с настоящим примерно в 6% случаев | подделка обязана гарантированно отличаться |
| `403 access_denied` от Google | приложение в режиме Testing, а аккаунт не в списке тестировщиков | Auth Platform → Audience → Test users |
| Google показывает «приложение colmogravity.net» | это **наш** домен: у непроверенного приложения Google показывает домен вместо имени | не паниковать, проверить `client_id` |

## 7. Google / OAuth

- Проект `welcome-p0` (ID `my-project-48009welcome-p0`), клиент `welcome-web`,
  redirect URI: `https://welcome.colmogravity.net/api/oauth/google/callback` и
  `http://localhost:3000/api/oauth/google/callback`.
- В режиме Testing пускают только тестировщиков. Чтобы пускать всех — заполнить
  брендинг (домашняя страница и политика) и нажать **Publish app**; Google будет
  показывать предупреждение «приложение не проверено» до прохождения ревью.
- Консоль Google плохо поддаётся автоматизации: кнопки Save/Publish вне дерева
  доступности, диалоги открываются по «клик + Enter». Это ограничение инструмента,
  а не кода продукта.
